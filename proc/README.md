# Процессы в Linux

Конспект по теме "Процессы в Linux" — программы, процессы, демоны, зомби, сироты, каталог /proc и системные вызовы для управления процессами.

## Программа vs процесс

Программа — это пассивный набор инструкций, который лежит на диске в виде файла. Процесс — это уже запущенная программа: у неё есть PID, своё адресное пространство, стек, регистры и всё, что нужно для реального выполнения.

Одна и та же программа может породить сразу несколько процессов одновременно (например открыл три вкладки браузера — это три разных процесса от одного и того же бинарника).

## Системные вызовы для управления процессами

Это обращение прикладной программы к ядру ОС. Именно через них процессы создаются, запускаются, завершаются и получают результат работы друг друга.

### fork() — единственный способ создать процесс в Linux

fork() не запускает что-то новое с нуля, а **клонирует** вызывающий процесс. После fork() есть два почти идентичных процесса — родитель и потомок, оба продолжают выполнение с той же строки кода, где был вызван fork(). Различить их можно только по возвращаемому значению:
- родителю fork() возвращает PID потомка
- потомку fork() возвращает 0

Пример: когда в bash вводишь команду `ls`, bash делает fork() — то есть клонирует сам себя.

### exec() — способ запустить программу в Linux

exec() работает в уже существующем процессе — не создаёт новый, а **заменяет** программу процесса на ту, что передана в exec() в качестве аргумента. PID остаётся тот же, но внутри теперь другая программа.

Связка получается такая: bash делает fork() → в дочернем процессе (клоне bash) вызывает exec("/bin/ls") → клон bash "превращается" в ls, оставаясь тем же процессом по PID. Это и есть механизм запуска любой команды в shell.

exec() — семейство системных вызовов: execl, execle, execlp, execv, execve, execvp.

### exit() — завершение работы программы

Приводит к обычному завершению программы. После завершения программы её переменная status (код возврата) будет доступна родительскому процессу.

Важный момент: exit() **не завершает процесс полностью**. Он переводит его в состояние зомби и оставляет код возврата доступным для родителя — процесс исчезает из системы только после того, как родитель заберёт этот код через wait().

### wait() — считывает код возврата дочернего процесса

Приостанавливает выполнение текущего процесса до тех пор, пока дочерний процесс не прекратит выполнение. Получает код возврата дочернего процесса. После вызова wait() дочерний процесс полностью исчезает из системы.

### Жизненный цикл процесса целиком

```
fork() → [Parent → wait()] 
       → [Child → exec() → exit()] → возврат к wait() → resumes
```

Пример на `ls`:
1. Вводишь `ls` в bash
2. bash делает fork() — клонирует себя
3. В клоне вызывается exec() — клон превращается в ls
4. ls выполняет работу, печатает список файлов
5. ls вызывает exit() — на мгновение становится зомби
6. bash (родитель) вызывает wait() — забирает код завершения, зомби исчезает
7. bash продолжает жить, ждёт следующую команду

## Некоторые состояния процессов

- **R** — выполняется в данный момент
- **S** — процесс ожидает
- **D** — ожидает ввода-вывода
- **T** — процесс остановлен
- **Z** — процесс зомби

## Демон

Процесс, работающий в фоновом режиме без прямого взаимодействия с пользователем. sshd, httpd, ftpd и подобные — программы, работающие в режиме демона (последняя буква "d" в названии означает daemon).

Демон обычно делает двойной fork (демонизацию), отвязывается от управляющего терминала и становится сиротой, которую усыновляет init/systemd — так он живёт независимо от того, кто его запустил.

## Зомби

Обязательное состояние **любого** процесса — эта стадия возникает у каждого процесса без исключения при завершении. Процессы-зомби не потребляют ресурсы (нет памяти, нет открытых файлов, нет исполняемого кода) — это просто запись в таблице процессов (PID + код возврата), которая ждёт, пока родитель её заберёт. Процесс зомби нельзя убить (завершить) — там нечего убивать, ничего не выполняется.

Зомби зависает надолго только в одном случае: **родитель жив, но не вызывает wait()** (баг в коде родителя, забыл собрать результат ребёнка). Если видно много `Z` в `ps aux` — это сигнал, что где-то в родителе баг.

### Как "убить" зомби

- сделать его сиротой (родитель умирает → сирота мгновенно переусыновляется на PID 1 → PID 1 сразу делает wait())
- заставить родителя вызвать wait()

## Сирота

Процесс, оставшийся без родителя (родитель умер **раньше**, чем ребёнок закончил работу). Будет мгновенно усыновлён процессом init (в современных системах — systemd). Явление очень кратковременное — увидеть процесс-сироту почти невозможно, потому что переусыновление происходит практически мгновенно.

Важно: сирота — это **не зомби**. Сирота продолжает нормально работать (у неё родитель просто сменился на PID 1), и только когда сирота сама закончит работу и вызовет exit() — она на мгновение станет зомби. Но поскольку её новый родитель (systemd) всегда сразу вызывает wait() за своих детей — зомби мгновенно исчезает, увидеть его почти нельзя.

## Каталог /proc

`/proc` — это не настоящая файловая система на диске, а виртуальная, которую ядро генерирует на лету прямо в памяти. Когда обращаешься к любому файлу внутри — ядро в этот самый момент собирает актуальную информацию и отдаёт её как текст. Данные там всегда свежие, а не устаревший кэш.

Внутри `/proc` лежат:
- каталоги с числовыми именами (1, 2, 1026...) — PID'ы работающих процессов
- обычные файлы/каталоги со словами (cpuinfo, meminfo, mounts, net, uptime, version...) — общесистемная информация, не привязанная к конкретному процессу

### /proc/PID/status — человекочитаемая информация о процессе

Самый "дружелюбный к человеку" файл — с подписанными полями, легко читается глазами:
- **Name** — короткое имя процесса
- **State** — состояние (R/S/D/Z/T)
- **Pid** — собственный PID
- **PPid** — PID родителя
- **Uid/Gid** — от какого пользователя и группы запущен (четыре нуля = root)
- **VmSize** — виртуальная память ("забронировано")
- **VmRSS** — реальная физическая память, занятая прямо сейчас ("реально занято")
- **VmPeak** — пиковое значение виртуальной памяти за всё время
- **FDSize** — сколько дескрипторов зарезервировано

### /proc/PID/cmdline — с какими параметрами запущен процесс

Хранит аргументы командной строки, разделённые не пробелом, а **нулевым байтом** (`\0`) — потому что сам аргумент может содержать пробел внутри себя (например путь с пробелом), и нулевой байт гарантированно не встретится внутри текста аргумента.

Чтобы прочитать читаемо:
```bash
cat /proc/PID/cmdline | tr '\0' ' '; echo
```
`tr '\0' ' '` заменяет каждый нулевой байт на обычный пробел. Без этого все аргументы слипаются в одну кашу на экране.

cmdline показывает **всю команду целиком** — и имя программы, и все параметры, с которыми она была запущена. Это не то же самое, что Name/comm (только имя без параметров) — cmdline даёт понять, что конкретно делает процесс.

### /proc/PID/fd/ — что процесс держит открытым прямо сейчас

Список всех файловых дескрипторов процесса — то, с чем процесс **сейчас взаимодействует** (живой снимок, не история). Каждый дескриптор — это симлинк на:
- обычный файл на диске
- терминал (`/dev/pts/N`)
- сокет (`socket:[инод]`)
- специальное устройство (`/dev/null`)
- анонимный inode (`anon_inode:inotify` — механизм уведомлений ядра)

Стандартные дескрипторы у любого процесса:
- **0** — stdin (откуда читает)
- **1** — stdout (куда пишет результат)
- **2** — stderr (куда пишет ошибки)
- **3 и дальше** — всё, что процесс дополнительно открыл сам

Практическое применение: диагностика "диск забит, но rm не помог" — `rm` только убирает имя файла из каталога (unlink), а данные физически остаются, пока хотя бы один процесс держит файл открытым через дескриптор (счётчик ссылок на inode не равен нулю). Найти виновника:
```bash
lsof | grep deleted
```

### /proc/PID/stat — сырые данные одной строкой, для скриптов

Вся информация в одну строку через пробел, без подписей — именно этот файл читают `ps`/`top`, потому что парсить одну строку быстрее программно, чем текстовый файл с метками.

Важные поля по номерам:
| № поля | Значение |
|---|---|
| 1 | PID |
| 2 | имя команды, в круглых скобках |
| 3 | состояние (R/S/D/Z/T) |
| 4 | PPID |
| 14 | utime — время в пользовательском режиме (тики) |
| 15 | stime — время в режиме ядра (тики) |
| 19 | nice-значение |

Нюанс: если имя процесса в поле 2 само содержит пробелы — простой awk по номеру поля может сбиться, потому что пробел внутри скобок сдвинет нумерацию.

### /proc/PID/comm и /proc/PID/exe

- **comm** — только короткое имя процесса, отдельным маленьким файлом (то же самое, что Name в status, но без похода в длинный файл)
- **exe** — симлинк на реальный путь до исполняемого файла на диске. Полезно после обновления пакетов — если там видна пометка `(deleted)`, значит бинарник на диске уже заменили, а процесс всё ещё работает со старой версией в памяти — сигнал, что процесс нужно перезапустить

### /proc/net/ и /proc/mounts

`/proc/net/tcp` — сырые данные о TCP-соединениях (адреса и порты в hex, неудобно читать глазами напрямую). `/proc/mounts` — список примонтированных файловых систем, текстом, читается нормально.

Общий паттерн для всего /proc: это источник сырых данных для ядра, а не инструмент для повседневной ручной работы. Почти всегда есть удобная утилита, которая уже сама читает нужные файлы из /proc и показывает результат по-человечески:

| Что нужно узнать | Сырой источник в /proc | Удобная утилита поверх |
|---|---|---|
| Процессы | stat, status | ps, top |
| Открытые файлы/сокеты | PID/fd/ | lsof |
| Сетевые соединения | net/tcp | ss, netstat |
| Примонтированные ФС | mounts | mount, df -h |
| Память системы | meminfo | free -h |

## nice — приоритет процесса

Утилита, которая запускает программу с определённым приоритетом планировщика CPU — насколько сильно процесс должен уступать место другим процессам, когда несколько программ одновременно борются за процессорное время.

Диапазон: от **-20** (самый высокий приоритет) до **19** (самый низкий, самый "уступчивый"). 0 — приоритет по умолчанию.

```bash
nice -n 10 sleep 100      # запустить новый процесс с nice=10
renice -n 5 -p PID         # изменить nice уже запущенного процесса
```

Обычный пользователь может только повышать число (понижать свой же приоритет), понижать (уходить в минус, повышать приоритет) может только root.

Приоритет реально проявляется только тогда, когда несколько процессов **конкурируют** за CPU одновременно — если CPU свободен, процесс с nice=19 работает с той же скоростью, что и с nice=0.

## Утилиты — ps, top, pstree, pgrep/pidof, ss

### ps

- `ps` (без опций) — только процессы текущего терминала
- `ps aux` — стандарт на 90% случаев: все процессы (`a`), с деталями по CPU/памяти (`u`), включая процессы без терминала (`x`)
- `ps -ef` — то же самое, другой стиль колонок (BSD vs System V)
- `ps -efl` — расширенный формат, добавляет NI (nice) и S (state) в одной команде
- `ps aux --sort=-%cpu` / `--sort=-%mem` — сортировка по потреблению ресурсов
- `ps auxf` — дерево прямо в обычном выводе ps

ps — это статичный снимок на момент запуска команды, не обновляется сам.

### top

Показывает процессы живьём, с автообновлением (по умолчанию раз в секунду).

Верхние строки:
- `load average: 0.15, 0.10, 0.05` — средняя загрузка системы за 1/5/15 минут. При 1 ядре CPU load=1.0 означает загрузку на 100%
- `Tasks: ... running, sleeping, stopped, zombie` — количество процессов в каждом состоянии
- `%Cpu(s): us, sy, ni, id, wa, hi, si, st` — user/system/nice/idle/iowait и т.д. Высокий `wa` = диск тормозит систему

Горячие клавиши: `P` — сортировка по CPU, `M` — по памяти, `k` — убить процесс, `r` — renice, `f` — управление отображаемыми колонками (пробел включает/выключает), `W` — сохранить настройки, `q` — выйти.

### pstree

Показывает иерархию процессов деревом, а не плоским списком — не нужно вручную сопоставлять PID/PPID.

```bash
pstree -p              # с PID в скобках у каждого процесса
pstree -p 1026          # дерево от конкретного PID вниз
pstree -pa 1026         # + полная командная строка с аргументами
```

Поиск по имени процесса (`pstree sshd`) не всегда работает стабильно — надёжнее искать PID через pidof и подставлять число.

### pidof / pgrep

`pidof` — простой поиск PID по точному имени процесса, ничего больше.

`pgrep` — то же самое плюс гибкие фильтры:
```bash
pgrep -u root sshd        # только процессы sshd, запущенные от root
pgrep -f "sleep 300"       # поиск по полной командной строке, а не только по имени
pgrep -l sshd              # вывести имя рядом с PID
```

`-f` критически полезен, когда несколько процессов имеют одинаковое имя, но разные аргументы — обычный `pgrep sleep` найдёт все процессы sleep, а `pgrep -f "sleep 300"` — только тот, что запущен именно с этим параметром.

### ss — сеть, порты, соединения

`ip a` показывает только адреса интерфейсов — ничего не говорит о том, какие процессы что слушают. Для этого нужен ss.

```bash
ss -tlnp    # t=TCP, l=только LISTEN, n=числа портов вместо имён, p=какой процесс
ss -tnp     # без l — покажет ещё и установленные (ESTAB) соединения
```

LISTEN означает "процесс открыл порт и ждёт подключения, но реального обмена данными ещё нет". ESTAB — конкретное активное соединение с конкретным клиентом.

## Своя реализация ps ax (домашнее задание)

Задание: написать свою реализацию `ps ax`, используя анализ `/proc`, без сторонних утилит вроде ps/top.

Логика:
1. Перебрать `/proc/[0-9]*` — glob-шаблон сразу отсекает все нечисловые записи (net, self, cpuinfo и т.д.), поэтому отдельная regex-проверка не нужна
2. Из имени каталога вырезать чистый PID через `${entry##*/}`
3. Для каждого PID прочитать `/proc/$pid/stat` — оттуда взять STATE (поле 3), utime и stime (поля 14, 15) для расчёта TIME
4. Из `/proc/$pid/comm` взять имя процесса
5. Для TTY — прочитать через `readlink`, куда ведёт `/proc/$pid/fd/0`; если это `/dev/pts/N` — обрезать префикс `/dev/` через `${tty#/dev/}`; если это что-то другое (null, сокет) или дескриптора вообще нет (ядерные потоки) — выводить `?`
6. Вывести всё через `printf` с фиксированной шириной колонок для ровной таблицы
7. Отсортировать по PID через `sort -n`, применённый ко всему выводу цикла (сортировка после `done`, потому что sort должен видеть весь набор данных сразу, а не по одной строке за раз)

Разница в пару единиц между `wc -l` своего скрипта и `ps ax` — нормальна: заголовок в ps добавляет +1, живая система постоянно меняется, а собственный скрипт по ходу работы сам порождает bash/awk/sort-процессы, которые тоже попадают в /proc в момент снятия снимка.

### script.sh

```bash
#!/bin/bash

printf "%-8s %-4s %-40s %-6s %-10s\n" "PID" "STAT" "COMMAND" "TIME" "TTY"

for entry in /proc/[0-9]*; do
    pid="${entry##*/}"
    state=$(awk '{print $3}' "/proc/$pid/stat")
    name=$(cat /proc/$pid/comm)
    time1=$(awk '{print $14}' "/proc/$pid/stat")
    time2=$(awk '{print $15}' "/proc/$pid/stat")
    time3=$(( (time1 + time2) / 100 ))
    tty=$(readlink /proc/$pid/fd/0 2>/dev/null)
    tty="${tty#/dev/}"
    if [[ ! $tty =~ ^(pts|tty) ]]; then
        tty="?"
    fi
    printf "%-8s %-4s %-40s %-6s %-10s\n" "$pid" "$state" "$name" "$time3" "$tty"
done | sort -n
```

Запуск:
```bash
bash script.sh
```
