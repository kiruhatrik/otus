# Systemd

## Что вообще такое

Systemd — это система инициализации, то есть то, что запускает всю систему после ядра.
Пришла на замену старому SysV (там были run level'ы, линейный запуск без параллельности и без автоперезапуска при падении процесса).

Главные плюсы перед SysV:
- сервисы запускаются параллельно, а не по очереди
- есть зависимости между сервисами
- если процесс упал — можно настроить автоперезапуск
- логи в одном месте (journalctl), не надо руками парсить текстовые файлы

## Как грузится система (по шагам)

1. Power on → BIOS/UEFI делает POST
2. Ищется загрузчик в MBR (BIOS) или на ESP-разделе (UEFI, GPT)
3. GRUB подгружает в память ядро + initrd
4. Ядро распаковывается и стартует
5. initrd — временная файловая система, нужна чтобы подгрузить драйверы и найти настоящий диск
6. switch_root — переключение с initrd на реальный корень `/`
7. Ядро запускает `/sbin/init` (это симлинк на `/lib/systemd/systemd`) — это PID 1
8. systemd параллельно поднимает юниты, двигаясь к target'у по умолчанию (обычно multi-user.target)

## Targets

Target — это НЕ демон и не процесс. У него даже нет секции `[Service]`. Это просто чекпоинт/веха — список того, что должно быть готово к определённому моменту.

Основные:
- `multi-user.target` — обычный многопользовательский режим с сетью (и графика туда входит тоже, просто добавляется сверху)
- `rescue.target` — аналог single user из SysV
- `graphical.target` — требует multi-user.target + добавляет графику

Путь: `sysinit.target → basic.target → multi-user.target → graphical.target`

Важно: `timers.target` и `sockets.target` цепляются рано, через `basic.target` — ещё ДО multi-user.target. Поэтому у таймеров `WantedBy=timers.target`, а не multi-user.target — не потому что это "альтернатива", а потому что это более ранняя ступенька на пути к тому же multi-user.target.

## Типы юнитов (какие бывают, но реально юзаю в основном .service и .timer)

- `.service` — запуск процесса/демона
- `.timer` — замена cron
- `.target` — группировка
- `.socket` — активация по подключению к сокету
- `.mount` / `.automount` — точки монтирования
- остальное (`.device`, `.path`, `.slice`, `.swap`) — руками почти не пишу, но знать что есть надо

## Где лежат юниты

- `/lib/systemd/system/` — юниты из пакетов (apt install). **Не трогать!** Перезапишется при обновлении пакета.
- `/etc/systemd/system/` — свои юниты. Сюда всё и пишу.

Если файл с одинаковым именем есть в обоих местах — побеждает `/etc/`.

## Type= в [Service] — самое важное

- `simple` (дефолт) — процесс просто живёт на переднем плане, никакого форка. PID = PID.
- `oneshot` — разовая команда, должна САМА завершиться. Если хочу чтобы после завершения юнит показывался как active, а не dead — добавляю `RemainAfterExit=yes`.
- `forking` — процесс сам вызывает fork(), родитель завершается, а потомок живёт дальше как демон. Тут ОБЯЗАТЕЛЬНО нужен `PIDFile=`, чтобы systemd понял какой именно PID теперь главный.

Как понять какой Type нужен: смотрю что делает программа. Завершается сама — oneshot. Живёт вечно на переднем плане — simple. Форкается сама в фон (это видно по функции типа `daemon` в старых init-скриптах, или по флагу `--background`/наличию pidfile в оригинальном скрипте) — forking.

## start vs enable — две независимые вещи

- `systemctl start` — запускает сервис ПРЯМО СЕЙЧАС. После reboot сам не поднимется.
- `systemctl enable` — создаёт симлинк в `/etc/systemd/system/<target>.wants/`, чтобы сервис поднимался автоматически при следующей загрузке. Само по себе ничего не запускает.
- `enable --now` — и то и то сразу.

Секция `[Install]` в файле юнита ничего не активирует сама по себе — она просто говорит команде `enable`, куда класть симлинк, когда её вызовут.

## EnvironmentFile — как конфиг попадает в скрипт

Порядок действий (это долго не мог понять, но разобрался):

1. Пишу конфиг `/etc/default/имя` с переменными типа `WORD=ALERT`
2. В юните пишу `EnvironmentFile=/etc/default/имя`
3. systemd САМ читает этот файл ДО запуска процесса
4. В `ExecStart=` пишу `$WORD` — systemd подставляет туда реальное значение из конфига
5. Только ПОСЛЕ этой подстановки процесс реально стартует — то есть скрипт получает уже готовую команду типа `/opt/script.sh ALERT /var/log/watchlog.log`
6. Скрипт видит это просто как `$1` и `$2`, он вообще не знает что где-то есть файл конфига

Скрипт не читает конфиг сам — это делает только systemd, скрипт получает уже готовые аргументы.

## Зачем разделять конфиг / скрипт / таймер, если можно всё захардкодить

- конфиг можно менять без риска сломать логику
- один и тот же скрипт можно переиспользовать с разными параметрами (второй watchlog под другой лог — просто новый конфиг + новый юнит, скрипт трогать не надо)
- под это удобно заводить автоматизацию (Ansible и т.д.) — генерить конфиги проще и безопаснее, чем лезть внутрь скрипта

## Таймеры

```ini
[Timer]
OnActiveSec=0        # сработать сразу при активации таймера
OnUnitActiveSec=30    # дальше повторять через 30 сек после последнего запуска сервиса
Unit=имя.service       # какой сервис дёргать (если не указано - берёт юнит с таким же именем)
```

Без `OnActiveSec=0` первый запуск случится только через N секунд ожидания — потому что `OnUnitActiveSec` отсчитывает от "прошлого запуска", а его в первый раз просто не было.

`OnCalendar=` — если нужно точное время (типа cron), а не интервал. Там своя точка отсчёта, `OnActiveSec` не нужен.

## journalctl — куда смотреть логи

- `journalctl -u имя.service` — показывает служебную инфу юнита + stdout/stderr процесса
- НО если скрипт использует `logger`, а не `echo` — сообщение туда НЕ попадёт! `logger` пишет со своим тегом (обычно по имени юзера), а не от имени юнита. Искать через `journalctl -t root` или `journalctl -t свой_тег`.
- Для учебных целей проще использовать `echo` внутри скрипта — тогда всё видно сразу через `-u`.

## Шаблоны юнитов (nginx@.service)

Файл с `@` перед расширением (`nginx@.service`) — это шаблон.
Запускаю: `systemctl start nginx@first` — слово после `@` подставляется в файл шаблона вместо `%i`.

Важно: `%i` — это просто текстовая подстановка твоего слова из команды запуска, к номеру процесса (PID) отношения не имеет. Нужен чтобы у разных экземпляров были разные пути (pid-файл, конфиг), не пересекались.

Что обязательно должно отличаться между инстансами:
- **порт** — иначе второй процесс не запустится, порт уже занят первым
- **pid-файл** — иначе второй перезапишет pid первого, и systemd потеряет какой PID к какому юниту относится (грабля на которую наступил: PIDFile в юните и `pid` директива внутри конфига nginx должны СОВПАДАТЬ, иначе висит с ошибкой "Can't open PID file")
- root-папка — не обязательно технически, но иначе оба будут отдавать одно и то же
