# SELinux — конспект

## Зачем вообще

Обычные права Linux (`rwx`, владелец, группа) называются **DAC**. Их минус: программа может всё, что может её пользователь. Взломали nginx от root — у хакера всё.

**SELinux** — это **MAC** (мандатный доступ), второй замок поверх `rwx`. Он смотрит не на пользователя, а на то, **какая это программа**, и пускает её только туда, где это прописано в политике. Всё, что не разрешено, запрещено, даже root.

Доступ будет, только если пустили **оба** замка:
```
процесс → 1) права rwx → 2) SELinux → доступ
```

Это не делает взлом невозможным, но запирает хакера в той маленькой комнате, которая нужна самой программе.

Разработан АНБ США, есть в RHEL/AlmaLinux/Rocky/Fedora. В Debian/Ubuntu вместо него AppArmor.

## Как устроен — 3 части

1. **Метки (бейджики)** — у каждого процесса и каждого файла (и порта). У файлов хранятся на диске в расширенных атрибутах, точка в `-rw-r--r--.` значит "метка есть"
2. **Политика (книга правил)** — правила вида "тип процесса может действие над типом объекта". Уже лежит в системе, писать её с нуля не нужно
3. **Охранник в ядре + журнал** — на каждое действие ядро спрашивает SELinux. Каждое "нет" пишется в `/var/log/audit/audit.log` как **AVC**

## Метка

```
system_u : object_r : httpd_sys_content_t : s0
  user       role          TYPE            level
```
На практике смотрю **только тип** — третье поле, на `_t`. Остальное служебное: `user` — кто создал (`system_u` система, `unconfined_u` я), `role` — `object_r` у файлов, `system_r` у процессов, `s0` — уровни секретности (в targeted не используются).

Тип у процесса называют **доменом**.

Правило в политике:
```
httpd_t  может  read  httpd_sys_content_t
```

Типы одного сервиса — это отдельные таблички, не вложенные друг в друга. У веб-сервера (все веб-серверы, и nginx тоже, это `httpd`):
- `httpd_t` — процесс
- `httpd_exec_t` — бинарник `/usr/sbin/nginx`
- `httpd_config_t` — конфиги
- `httpd_sys_content_t` — сайт, только чтение
- `httpd_sys_rw_content_t` — сайт, можно писать (загрузки)
- `httpd_log_t` — логи
- `http_port_t` — порты 80, 443...

## Переход контекста

Как процесс получает домен: файл `sshd_exec_t` — "входная дверь". Запустил файл такого типа — новый процесс перешёл в домен `sshd_t`. Пример: пользователь (`unconfined_t`) запускает `passwd` (`passwd_exec_t`) → процесс в `passwd_t` → ему можно писать `/etc/shadow` (`shadow_t`), и больше никуда.

## Режимы и политики

| Режим | Что делает |
|---|---|
| **Enforcing** | запрещает и пишет в журнал (боевой) |
| **Permissive** | ничего не запрещает, но пишет "я бы запретил" (отладка) |
| **Disabled** | выключен |

```bash
getenforce / sestatus      # текущий режим
setenforce 0 / 1           # permissive / enforcing до перезагрузки
/etc/selinux/config        # режим после перезагрузки
```
Как `systemctl start` и `enable`: одно про "сейчас", другое про "после загрузки".

Политики: **targeted** (по умолчанию — жёстко ограничены сервисы, пользователи почти нет, `unconfined_t`), minimum, mls (уровни секретности для гос/военных: "no read up, no write down").

## Откуда берётся метка у файла

- **создал** файл в папке (`echo >`, `cp`, редактор) → берёт **тип папки**
- **перенёс** через `mv` → привозит **старую** метку. Самая частая причина проблем
- `restorecon` → ставит метку по **справочнику** "путь → тип" (`semanage fcontext -l`)

## Когда что-то не работает

Причина всегда одна из двух:
1. **у файла/порта не та табличка** → чиню табличку
2. **табличка правильная, но в правилах нет пункта** → переключатель или свой модуль

Алгоритм:
```
1. Заметил ошибку (403, SERVFAIL, сервис не стартует)
2. Проверил rwx — если пускают, подозреваю SELinux
3. Журнал сервиса:  journalctl -u сервис
4. Журнал SELinux:  ausearch -m avc -ts recent   (recent = 10 мин, шире: today)
5. Читаю AVC: { что } scontext=кто tcontext=к чему tclass=объект
6. Фильтрую шум: смотрю comm и scontext — моя ли это программа
7. Решаю: табличка или правило → чиню → проверяю
```

`SERVFAIL` vs `REFUSED` у DNS: REFUSED — "тебе нельзя" (клиент/конфиг), SERVFAIL — "я сломался" (ищи на сервере).

### Как узнать нужный тип, если не помню

- **подсмотреть у того, что работает**: `ls -Zd /usr/share/nginx/html`, `semanage port -l | grep -w 80`
- **спросить книгу правил**: `sesearch -A -s httpd_t -c tcp_socket -p name_bind` — слова берутся прямо из AVC (кто, объект, действие)
- **спросить подсказку**: `ausearch ... | audit2why`, `journalctl -t setroubleshoot`. Но думать всё равно мне: подсказка часто предлагает "просто разрешить", а правильно починить табличку

## Инструменты

| Задача | Команда |
|---|---|
| Метка файла / процесса | `ls -Z`, `ls -Zd папка`, `ps -eZ`, `id -Z` |
| Отказы SELinux | `ausearch -m avc -ts recent` |
| Почему отказ и чем лечить | `ausearch -m avc -ts recent \| audit2why` |
| Вернуть метку по справочнику | `restorecon -Rv путь` (`-n` — только показать) |
| Своя папка: правило в справочник | `semanage fcontext -a -t тип "/путь(/.*)?"` + `restorecon -Rv /путь` |
| Только мои правила | `semanage fcontext -l -C` |
| Временно сменить метку (проверить гипотезу) | `chcon -t тип путь` — откатится при `restorecon` |
| Переключатели | `getsebool -a`, `setsebool -P имя on` (`-P` — навсегда) |
| Порты | `semanage port -l`, `semanage port -a -t тип -p tcp порт`, `-d` удалить свой |
| Свой модуль | `audit2allow -M имя` → **прочитать `имя.te`** → `semodule -i имя.pp` |
| Поиск правил | `sesearch -A -s домен ...`, `seinfo` |

Пакеты (EL9): `policycoreutils-python-utils` (semanage, audit2why, audit2allow), `setools-console` (sesearch, seinfo), `setroubleshoot-server` (человеческие объяснения).

## Типичные случаи из практики

| Ситуация | Решение |
|---|---|
| Файл сайта перенесли через `mv` → 403 | `restorecon -v файл` |
| Сайт в своей папке (`/site`) → 403 | `semanage fcontext -a -t httpd_sys_content_t "/site(/.*)?"` + `restorecon` |
| nginx на нестандартном порту не стартует (`bind ... Permission denied`) | `semanage port -a -t http_port_t -p tcp 4881` (точечно, лучший вариант) |
| То же через переключатель | `setsebool -P nis_enabled 1` — открывает ВСЕ ничейные порты, широко |
| nginx как прокси → 502 | `setsebool -P httpd_can_network_connect 1` |
| Сервис пишет в каталог конфигов | переложить данные в штатный каталог для записи (DNS: `/var/named/dynamic`) |

Порт: SELinux решает, **можно ли** сесть на порт. На каком порту сервис **слушает** — его конфиг. Можно ли подключиться **снаружи** — firewall. Три разные вещи.

## Главное

- SELinux почти никогда не "сломан" — он защищает. Обычно неправ файл (не там лежит или не та метка)
- Класть данные в стандартные места — и SELinux почти не мешает
- `setenforce 0` / `SELINUX=disabled` — не решение, а снятая с петель дверь
- `audit2allow` — последний вариант, и только после того, как прочитал, что он разрешает
