# Механизмы изоляции и аккаунтинга Linux

Конспект по теме: chroot, namespaces, cgroups. По сути это фундамент перед Docker — разбираюсь, из чего вообще сделан контейнер.

## Главная мысль

Контейнер — это **не мини-виртуалка**. Это обычный процесс на обычном ядре хоста. Ядро одно на всех. Просто процессу навесили ограничения:

```
Контейнер = namespaces + cgroups + свой корень (файлы образа)
             (что видит)  (сколько ест)  (какие файлы)
```

- **namespaces** — стены. Решают, **что процесс видит** (только своё)
- **cgroups** — счётчики и лимиты. Решают, **сколько процесс может потратить** (CPU, память, диск)

Это два независимых механизма. namespaces ничего не ограничивают по ресурсам, cgroups ничего не прячут. Контейнер получается, только когда работают оба.

Зачем всё это: защищённый режим (тема памяти) уже изолировал процессам **память**. Но всё остальное было общим: один `/`, один список процессов, одна сеть, один hostname, и никаких лимитов. Эта тема закрывает именно это.

## chroot

**chroot (change root)** — подменяет процессу корень `/`. Процесс думает, что `/` это например `/root/jail`, и выше подняться не может.

Под капотом это очень простая штука: у процесса в ядре просто записано "твой корень вот тут". Видно через `/proc`:
```bash
ls -l /proc/PID/root     # у обычного процесса -> /, у процесса в chroot -> /root/jail
```

Появился в Unix v7 в 1979 году, изначально для удобства тестирования сборок, а не для безопасности.

### Где используется и сейчас
- тестирование программ в отдельной среде
- **восстановление системы**: загрузился с live-USB, примонтировал свой диск, сделал `chroot` в него и чинишь GRUB/пароль изнутри своей системы
- ограничение пользователя папкой (например SFTP)

### Недостатки
- **общие процессы** — из chroot видно и можно трогать все процессы системы
- **общая сеть** — два сервиса в двух chroot не сядут на один порт
- **нет лимитов** — процесс из chroot может съесть весь CPU и память
- **не защита** — root внутри chroot может из него выбраться

### pivot_root и jail
- **pivot_root** — более правильная смена корня: реально переставляет корневую ФС, старую можно отмонтировать. Сбежать сложнее. Его используют контейнерные движки. Похожее я уже видел при загрузке: `switch_root` с initrd на настоящий диск
- **FreeBSD jail** (1999–2000) — "chroot на стероидах": добавили изоляцию сети, на нём строили хостинги. Лимиты появились позже

### Практика: своя тюрьма с bash и ls

Главная ловушка: внутри тюрьмы **нет ничего** — ни программ, ни библиотек. Всё надо положить руками, **ровно по тем же путям**, что показывает `ldd`.

```bash
mkdir -p ~/jail/bin
cp /bin/bash /bin/ls ~/jail/bin/

ldd /bin/bash     # смотрю, какие библиотеки нужны
ldd /bin/ls
```

Вывод `ldd /bin/bash` у меня (Ubuntu):
```
linux-vdso.so.1                     <- не файл, его ядро подсовывает само, копировать не надо
libtinfo.so.6 => /lib/x86_64-linux-gnu/libtinfo.so.6
libc.so.6     => /lib/x86_64-linux-gnu/libc.so.6
/lib64/ld-linux-x86-64.so.2         <- загрузчик, без него вообще ничего не стартует
```

```bash
mkdir -p ~/jail/lib/x86_64-linux-gnu ~/jail/lib64
cp -L /lib/x86_64-linux-gnu/{libtinfo.so.6,libc.so.6,libselinux.so.1,libpcre2-8.so.0} ~/jail/lib/x86_64-linux-gnu/
cp -L /lib64/ld-linux-x86-64.so.2 ~/jail/lib64/

chroot ~/jail /bin/bash
ls /          # видно только bin lib lib64 — для этого процесса это весь мир
```

На слайдах библиотеки лежат в `/lib64` — это пути из RHEL. В Ubuntu они другие, поэтому не копирую со слайда вслепую, а смотрю `ldd` у себя.

`libc.so.6` и загрузчик нужны и bash, и ls — второй раз их класть не надо. Поэтому они и называются **разделяемые** библиотеки.

### Грабли, на которые наступил

1. **Положил библиотеки не по тем путям** (в `jail/lib/` вместо `jail/lib/x86_64-linux-gnu/`) — бинарник внутри ищет их ровно там, где показал `ldd`.
2. **Скопировался симлинк вместо файла.** `/lib64/ld-linux-x86-64.so.2` в Ubuntu — это ссылка на `../lib/x86_64-linux-gnu/ld-linux-x86-64.so.2`. Внутри тюрьмы ссылка указывала в пустоту → загрузчика нет → `No such file or directory`, хотя bash на месте. Лечится `cp -L` (идти по ссылке и копировать сам файл). Проверять через `ls -l`: `l` в начале прав = симлинк.

По ошибке видно, где проблема:
- `failed to run command '/bin/bash': No such file or directory` — не нашёлся даже **загрузчик**, программа не стартовала
- `error while loading shared libraries: libselinux.so.1` — загрузчик **работает**, не хватает конкретной библиотеки, она прямо названа

## Namespaces

**Namespace** — возможность ядра выдать процессу **свою отдельную копию** глобального ресурса. Изменения внутри видят только процессы этого namespace.

Как я это запомнил — **пропуска в комнаты**. У **каждого** процесса всегда есть по одному пропуску в комнату каждого вида. У обычных процессов на сервере (sshd, cron, мой bash) пропуска в **одни и те же общие** комнаты — поэтому все видят всех. Контейнеру выдают пропуска в **новые, отдельные** комнаты.

Namespace = комната. "У контейнера несколько namespaces" = у него своя комната каждого вида. И можно смешивать: например `docker run --network host` — всё своё, а сеть общая с хостом.

### 7 типов

| Namespace | Что изолирует | Эффект |
|---|---|---|
| **Mount** | точки монтирования | свой набор ФС, свой `/` |
| **PID** | номера процессов | внутри свой PID 1, чужих не видно |
| **Network** | сеть | свои интерфейсы, IP, порты |
| **UTS** | hostname | своё имя хоста |
| **IPC** | межпроцессное общение | своя общая память, очереди |
| **User** | пользователи / UID | внутри root, снаружи обычный пользователь |
| **Cgroup** | вид на дерево cgroups | контейнер видит свою группу как корень |

Ловушка в названиях: **cgroup namespace — это не лимиты.** Это просто комната, которая прячет от контейнера общее дерево cgroups. Лимиты ставит механизм cgroups.

### PID namespace на примере nginx в Docker
Внутри контейнера `ps aux` покажет 2–3 процесса, а у nginx будет **PID 1**. На хосте тот же самый процесс виден с обычным PID, например 23456. **Один процесс — два номера**, смотря откуда смотреть. И внутри контейнера nginx играет роль PID 1: усыновляет сирот и собирает зомби.

### API — 3 системных вызова
- **`clone()`** — fork, который может сразу выдать потомку новые namespaces
- **`unshare()`** — текущий процесс отделяется в свой namespace
- **`setns()`** — **войти** в уже существующий namespace другого процесса (так работает `docker exec`)

### Утилиты
```bash
unshare --uts bash                 # запустить bash в новом UTS (своя комната имени). Нужен root!
unshare --pid --fork --mount-proc bash   # своя комната процессов
nsenter -t PID ...                 # зайти в namespace процесса
lsns                               # список namespaces
ls -l /proc/PID/ns                 # в каких комнатах процесс; число в [] — номер namespace
```

`--mount-proc` нужен потому, что `ps` берёт данные из `/proc`. Без свежего `/proc` он покажет все процессы хоста.

### Практика: свой hostname (UTS)
```bash
sudo -i
readlink /proc/1/ns/uts        # комната имени у systemd (общая)
unshare --uts bash
readlink /proc/$$/ns/uts       # номер ДОЛЖЕН отличаться
hostname test-container        # меняется только внутри
exit
hostname                       # снаружи старое имя
```

Грабля: `unshare` без root падает с `Operation not permitted`, а следующий `hostname test-container` выполняется уже в **общей** комнате и меняет имя **всему серверу**. Поэтому сначала сравниваю номера через `readlink` — разные, значит я в своей комнате.

Ещё: приглашение bash врёт — он запоминает hostname **в момент своего запуска**. Реальное имя смотреть командой `hostname`.

## cgroups (control groups)

Механизм ядра, который:
1. собирает процессы в **группы**
2. **ограничивает** группе ресурсы: CPU, память, диск, число процессов
3. **считает**, сколько группа реально потребила (это и есть "аккаунтинг")

В современных дистрибутивах — **cgroup v2** (одна общая иерархия).

### Как устроено
- **Дерево групп** видно как обычные папки в `/sys/fs/cgroup`. Это псевдо-ФС, как `/proc` — ядро генерит на лету
- **Каждый процесс — ровно в одной группе**
- **Ребёнок рождается в группе родителя** (наследует через fork). Ограничил группу nginx — все его воркеры тоже под лимитом
- Посмотреть группу процесса: `cat /proc/PID/cgroup` → строка вида `0::/user.slice/...`

### Контроллеры (что можно ограничивать)
- **cpu** — процессорное время
- **memory** — память
- **io** — дисковые операции
- **pids** — сколько процессов можно создать (защита от fork-бомбы)
- ещё cpuset, hugetlb, devices и др. (`cat /proc/cgroups`)

### Главные файлы внутри группы
- **`cgroup.procs`** — PID процессов в группе. Записал PID — процесс переехал
- **`cgroup.controllers`** — какие контроллеры доступны группе
- **`cgroup.subtree_control`** — включить/выключить контроллеры для дочерних групп (`+cpu`, `-memory`)
- **`cpu.max`** — потолок CPU. `50000` = 50 мс из каждых 100 мс = 50% одного ядра
- **`cpu.weight`** — вес при дележе CPU (1–10000)
- **`memory.max`** — жёсткий лимит памяти. Превысил → **OOM Killer, но только внутри этой группы**, остальной сервер живёт

### Пример: ограничить процесс до 50% CPU (со слайдов)
```bash
# процесс, который грузит CPU на 100%
sha1sum /dev/zero &

mkdir /sys/fs/cgroup/busy_group
echo 50000 > /sys/fs/cgroup/busy_group/cpu.max
echo <PID_sha1sum> > /sys/fs/cgroup/busy_group/cgroup.procs
top        # было 100%, стало ~50%
```

### nice vs cgroups
- `nice` (тема процессов) — "уступай соседям, если CPU тесно". Если CPU свободен, процесс всё равно ест сколько хочет
- `cpu.max` — **жёсткий потолок**. Даже если CPU свободен, выше лимита не поднимется

### Способы управления
- **руками через файлы** в `/sys/fs/cgroup` — трудоёмко
- `cgcreate`/`cgdelete` (libcgroup) — устарело
- **через systemd** — удобно и современно, так и делают

## cgroups через systemd

systemd сам раскладывает все процессы по дереву cgroups. Три вида юнитов:
- **service** — процессы, которые systemd запустил сам по юниту (`nginx.service`)
- **scope** — процессы, созданные снаружи: сессии пользователей, контейнеры, ВМ (`session-1.scope`)
- **slice** — папка для группировки. Процессов не содержит, только организует иерархию (`имя.slice`)

По умолчанию есть:
- `-.slice` — корень
- `system.slice` — системные сервисы
- `user.slice` — сессии пользователей
- `machine.slice` — контейнеры и виртуалки

### Команды
```bash
systemd-cgls          # дерево групп с процессами
systemd-cgtop         # кто сколько ест, по группам (как top, но по cgroups)

# временный (transient) сервис в своём slice
systemd-run --unit=test_unit --slice=test sha1sum /dev/zero

# лимиты на лету
systemctl set-property test_unit CPUQuota=50%
systemctl set-property test_unit MemoryHigh=500K
systemctl set-property test_unit MemoryMax=1M
```

### Постоянный лимит своему сервису — через drop-in
```ini
# /etc/systemd/system/persistent.service.d/20-cpu.conf
[Service]
CPUQuota=20%
Slice=persistent.slice
```
```bash
systemctl daemon-reload
systemctl restart persistent.service
```
`set-property` без `--runtime` тоже сохраняет лимит в drop-in, в `/etc/systemd/system.control/`.

Это связка с темой systemd: лимиты ресурсов — это просто ещё одни директивы в `[Service]`, а под капотом systemd пишет их в файлы `cpu.max` / `memory.max` нужной cgroup.

## Docker под капотом — как это всё складывается

```bash
docker run --memory 512m --cpus 1 -p 8080:80 nginx
```

| Часть | Механизм | Что происходит |
|---|---|---|
| запуск | PID namespace | nginx внутри — PID 1, чужих процессов не видит |
| запуск | Mount namespace + pivot_root | корень `/` — файлы образа nginx |
| запуск | UTS namespace | свой hostname (ID контейнера) |
| `-p 8080:80` | Network namespace | у контейнера свой 80 порт; зашёл на 8080 хоста — попал на 80 контейнера |
| `--memory 512m` | cgroup | больше 512 МБ не дадут, иначе OOM Killer внутри группы |
| `--cpus 1` | cgroup | не больше одного ядра |

Без лимитов Docker по умолчанию ничего не ограничивает — контейнер может съесть весь сервер.
