# NFS + Kerberos — конспект

## Что такое NFS

**NFS (Network File System)** — сетевая файловая система. Предназначена для быстрого расшаривания папки (т.е. без особой настройки), управляется на уровне пользователей через UID/GID в ОС Linux (а не через логины, как можно было бы подумать — совпадать должны именно числовые ID пользователя и группы на клиенте и сервере).

## Установка пакетов

Сервер:
```bash
apt install nfs-kernel-server
```

Клиент:
```bash
apt install nfs-common
```

## /etc/exports — основной файл конфигурации

Это файл, где прописывается, какие папки и кому расшариваются.

Пример:
```
/opt/folder *(rw,no_root_squash,no_subtree_check)
```

Применить изменения (перечитать файл):
```bash
exportfs -a
```

## Опции, которые можно указывать в exports

- **rw / ro** — разрешить чтение и запись или только чтение
- **sync / async** — отвечать на запросы только когда данные реально сохранены на диск, или не блокировать подключение, пока идёт запись
- **secure / insecure** — использовать для соединения только порты ниже 1024 или любые порты
- **root_squash / no_root_squash** — подменять запросы от root на анонимные, или не делать этого
- **subtree_check / no_subtree_check** — проверять попытки пользователя выйти за пределы экспортированной папки, или отключить эту проверку
- **nohide** — не скрывать поддиректории, если открыт доступ к нескольким каталогам
- **crossmnt** — похоже на nohide, но позволяет клиенту переходить с файловой системы, помеченной crossmnt, на смонтированные внутри неё файловые системы. То есть если дочерняя ФС «B» смонтирована внутри родительской «A», то crossmnt на «A» даёт тот же эффект, что и nohide на «B»
- **all_squash** — делать все запросы анонимными (не только от root)
- **anonuid** — какой uid использовать для анонимного пользователя
- **anongid** — какой gid использовать для анонимного пользователя

## Монтирование на клиенте

```bash
mount -t nfs 192.168.10.10:/opt/folder /mnt
```

## Kerberos — коротко

**Kerberos** — это система аутентификации через доверенную третью сторону. В отличие от обычного NFS (где сервер просто верит клиенту на слово, кто он такой, по UID), тут клиент должен предъявить криптографический билет, выданный отдельным сервером — KDC.

### Основные термины

- **KDC (Key Distribution Center)** — центральный сервер, который выдаёт билеты
- **REALM** — «территория доверия», у нас, например, `OTUS.COM`. Все, кто внутри одного realm, доверяют одному KDC
- **Principal** — идентификатор пользователя или сервиса внутри realm, например `vagrant@OTUS.COM` (пользователь) или `nfs/nfsserver.otus.com@OTUS.COM` (сервис)
- **TGT (Ticket Granting Ticket)** — «общий билет», который получаешь после `kinit`, дальше на его основе получаются билеты на конкретные сервисы
- **Keytab** — файл с ключом сервиса, чтобы сервис (например NFS) мог сам подтверждать себя автоматически, без ручного ввода пароля

### Основные команды

```bash
kinit vagrant       # получить билет (TGT) как пользователь vagrant
klist                # посмотреть какие билеты сейчас есть
kdestroy             # уничтожить билеты (разлогиниться)
```

Создание пользователя и сервисного principal (на KDC):
```bash
kadmin.local -q "addprinc vagrant"
kadmin.local -q "addprinc -randkey nfs/nfsserver.otus.com"
kadmin.local -q "ktadd -k /etc/krb5.keytab nfs/nfsserver.otus.com"
```

### Уровни защиты для NFS + Kerberos

- **krb5** — только аутентификация (проверка «кто ты»), данные передаются не зашифрованными
- **krb5i** — аутентификация + целостность (защита от подмены данных «по дороге»)
- **krb5p** — аутентификация + целостность + шифрование (самый защищённый вариант)

Пример строки в /etc/exports с Kerberos:
```
/opt/folder   *(rw,sync,fsid=0,no_subtree_check,sec=krb5i)
```

Монтирование на клиенте с Kerberos:
```bash
kinit vagrant
mount -t nfs4 -o sec=krb5i nfsserver.otus.com:/ /mnt/folder
```

### Важный нюанс

Для NFSv4 + Kerberos важно, чтобы на клиенте и сервере совпадал домен в `/etc/idmapd.conf` (параметр `Domain=`) — иначе сопоставление пользователей ломается, и всё «схлопывается» до анонимного пользователя, даже если билет получен успешно.

### Личный вывод

На практике голый Kerberos + NFS настраивают руками редко — обычно это скрыто внутри Active Directory или FreeIPA/ALD Pro, которые сами берут на себя всю возню с realm/keytab/idmapd. Но разобраться в механике полезно — когда встретишь AD/FreeIPA, будешь понимать, что происходит «под капотом», если аутентификация вдруг сломается.
