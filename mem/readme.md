# Память в Linux

Конспект по теме "Память в Linux" — эволюция памяти, реальный и защищённый режимы, кольца защиты, виртуальная память, страничная организация, кэш процессора, swap, /proc/sys/vm, HugePages.

## Зачем всё это понадобилось

Раньше программы напрямую работали с реальной физической памятью. Как только захотели запускать несколько программ одновременно — начался хаос: одна программа могла случайно залезть в память другой программы или в память самого ядра и всё сломать. Понадобилась защита.

## Реальный режим (real mode)

Самый первый режим работы процессоров x86 (с 8086, 1978 год), и именно в нём до сих пор **стартует** любой современный компьютер при включении.

Программа напрямую указывает физический адрес памяти, к которому хочет обратиться — никакой трансляции, никакой проверки прав. **Защиты памяти нет вообще** — даже память самого ядра была доступна любой программе на равных правах. Ошибка в программе могла обрушить всю систему, включая ядро.

Ограничение — может адресовать только 1 МБ памяти (20-битная адресная шина: 2²⁰ = 1 048 576 байт).

BIOS/UEFI при загрузке до сих пор частично написаны с расчётом на реальный режим — переключение в более сложные режимы происходит уже программно, в процессе загрузки (это делает загрузчик, например GRUB).

## Защищённый режим (protected mode)

Появился как ответ на проблему "ядро тоже не защищено". Что конкретно появилось:

1. **Кольца защиты** — уровни привилегий
2. **Гораздо больше адресуемой памяти** — 32-битная адресация (4 ГБ), современная 64-битная — намного больше
3. **Виртуальная память** — прослойка между программой и физической памятью
4. **Изоляция процессов друг от друга**

## Кольца защиты процессора

Архитектура 80286 (и выше) ввела 4 кольца, пронумерованных от 0 (максимум привилегий) до 3 (минимум):

- **Кольцо 0** — ядро ОС и драйверы
- **Кольцо 1** — оболочка операционной системы (в теории)
- **Кольцо 2** — менее важные части ОС (в теории)
- **Кольцо 3** — пользовательские приложения

**На практике кольца 1 и 2 никем не используются** — ни Windows, ни Linux, ни другие массовые ОС. Разработчики выбрали простую модель из двух реальных уровней: кольцо 0 (ядро) и кольцо 3 (всё остальное — systemd, bash, любые программы). Причины: производительность (каждое пересечение границы между кольцами — не бесплатная операция) и простота разработки.

Современные процессоры добавили ещё и **кольцо -1** (VMX root mode, Intel VT-x) — уровень ниже кольца 0, где работает гипервизор (KVM, VMware, VirtualBox) — он может контролировать даже ядро гостевой ОС.

### Как кольца связаны с памятью — бит U/S

У каждой страницы памяти в таблице страниц есть флаг **U/S** (User/Supervisor):
- **Supervisor** — страницу может трогать только код, выполняющийся в кольце 0
- **User** — страницу может трогать код в любом кольце

Процессор аппаратно, при каждом обращении к памяти, сверяет: в каком кольце сейчас работает код, и какой флаг у страницы. Если код в кольце 3 пытается тронуть страницу с флагом "только для ядра" — процессор физически блокирует операцию (segmentation fault).

Кольца — защита **инструкций** (что можно выполнять). Флаг U/S — защита **памяти** (что можно трогать). Два разных, но работающих вместе механизма.

### Как процесс обращается к ядру — системный вызов

Пример на systemd: он работает в обычном кольце 3, как и любой другой процесс. Когда ему нужно что-то привилегированное (создать процесс, смонтировать ФС, открыть сокет) — он не делает это сам, а вызывает системный вызов:

1. Процесс (кольцо 3) выполняет специальную инструкцию процессора (`syscall`)
2. Процессор аппаратно переключается из кольца 3 в кольцо 0, на заранее подготовленный ядром обработчик
3. Ядро (кольцо 0) выполняет операцию
4. Инструкция возврата (`sysret`) переключает процессор обратно в кольцо 3
5. Процесс продолжает работу с результатом

## Виртуальная память

Программа больше не работает с реальными физическими адресами. У неё есть своё **виртуальное адресное пространство** — огромная, "воображаемая" нумерация, доступная сразу целиком (на 64-битных системах — терабайты). Программа никогда не знает и не должна знать, где физически лежат её данные.

Два процесса могут использовать один и тот же виртуальный адрес (например оба думают, что у них есть адрес 0x1000) — физически это будут два разных места в памяти, потому что у каждого процесса своя личная таблица страниц.

## Страница (page)

Физическая память нарезана на одинаковые кусочки — **страницы**. Стандартный размер в Linux — **4 КБ**. Ядро оперирует не байтами, а целыми страницами — так компактнее и удобнее управлять памятью и вести таблицы соответствий.

## Таблица страниц (Page Table)

У каждого процесса — своя, отдельная, личная таблица, где записано соответствие: "вот этот виртуальный адрес процесса находится вот в этой физической странице". Ведёт эту таблицу **ядро**.

Быстрым чтением таблицы при каждом обращении к памяти занимается специальный блок в самом процессоре — **MMU (Memory Management Unit)**. Это происходит аппаратно и незаметно для программы.

Сама таблица физически тоже хранится в обычной физической памяти — это не отдельная "надстройка", а мостик между виртуальным и физическим слоями, который сам живёт в физической памяти.

Ядро не обязано класть физические страницы процесса рядом друг с другом — оно берёт любую подходящую свободную страницу, где бы она ни была. Фрагментация физической памяти абсолютно невидима для программы.

### Выделение памяти по требованию (lazy allocation)

Когда программа вызывает `malloc(1000)`:
1. Ядро резервирует диапазон виртуальных адресов — но физическая память на этом шаге ещё может не быть выделена
2. Только когда программа реально первый раз обращается к этому виртуальному адресу, процессор генерирует **page fault**
3. В этот момент ядро находит свободную физическую страницу и создаёт запись в таблице страниц

Виртуальная память не "заканчивается" и её не нужно "докупать" — виртуальных адресов всегда достаточно, это просто числа. Ограничен именно физический ресурс, и связь с ним устанавливается по факту реального использования.

### /proc/PID/maps — детальная разбивка виртуальной памяти

```bash
cat /proc/PID/maps
```
Показывает регионы виртуальной памяти (VMA) построчно: код исполняемого файла (с разными правами r--p / r-xp / rw-p для разных сегментов), heap (помечен `[heap]`), подключенные разделяемые библиотеки. Каждая строка — диапазон адресов с одинаковыми правами, сгруппированный из множества страниц по 4 КБ подряд.

VmSize в `/proc/PID/status` — это сумма всех таких регионов: сам бинарник + библиотеки + стек + куча.

## Грязные и чистые страницы (dirty / clean pages)

Если страница памяти связана с файлом на диске:
- **Чистая (clean)** — данные в памяти полностью совпадают с тем, что на диске
- **Грязная (dirty)** — в память внесли изменения, которые ещё не записаны на диск

**Сброс (flush/writeback) — это синхронизация памяти с диском.** До сброса есть расхождение, после — страница снова чистая. Команда `sync` делает это принудительно для всей системы.

Кто и когда сбрасывает — фоновые worker-потоки ядра (writeback), по двум правилам:
- **По времени** (`dirty_expire_centisecs`) — если страница грязная дольше N сотых секунды, сбросить принудительно
- **По объёму** (`dirty_background_ratio`, `dirty_ratio`) — если накопилось слишком много грязных данных

Если сервер резко выключится — все несохранённые изменения в грязных страницах теряются безвозвратно.

## free -m — разбор столбцов

```bash
free -m
```
```
              total   used   free   shared  buff/cache  available
Mem:            961    474    390        0         239        487
Swap:          2047      0   2047
```

- **total** — вся физическая память, видимая системой
- **used** — реально занято процессами прямо сейчас
- **free** — вообще ничем не занятая память (ни процессами, ни кэшем)
- **shared** — используется как общая между несколькими процессами
- **buff/cache** — кэш файловой системы (буферы, недавно прочитанные файлы). Не "потерянная" память — ядро может мгновенно освободить её, если реально понадобится
- **available** — реально доступная память для новых программ = free + вытесняемая часть buff/cache. Именно available, а не free, нужно смотреть, оценивая нехватку памяти

Почему `total` меньше заявленного объёма (например 1024 МБ выделено, а видно 961) — часть памяти забирает ядро и железо ещё в момент старта системы (код и структуры самого ядра, MMIO, служебные области), это не "резерв на будущее", а уже занятая память до того, как счётчики вообще начинают считать.

### drop_caches

```bash
echo 3 > /proc/sys/vm/drop_caches
```
Принудительно сбрасывает кэш файловой системы. Почти никогда не нужен в реальной эксплуатации — кэш это полезная оптимизация, а не проблема; он и так автоматически освобождается, когда реально нужен. Сброс имеет смысл разве что для чистых бенчмарков.

## Что происходит, когда физическая память заканчивается

1. **Swap** — ядро выгружает на диск давно неиспользуемые страницы (по алгоритму **LRU** — Least Recently Used, выгружаются те, что дольше всего не трогали), освобождая место
2. Если и swap не спасает — **OOM Killer** принудительно убивает процесс

### Swap подробнее

Swap касается той памяти, у которой нет "оригинала" на диске (данные кучи, переменные — то, что существует только в оперативке). Когда программа снова обращается к выгруженной странице — происходит page fault, ядро читает страницу обратно с диска (**swap in**) — это медленно, потому что диск в тысячи раз медленнее ОЗУ.

```bash
free -m                          # SwapFree vs SwapTotal
cat /proc/sys/vm/swappiness      # 0-100, приоритет ухода в swap
```
Чем выше swappiness — тем охотнее ядро уходит в swap. На серверах БД часто ставят низкое значение (например 10) — уход в swap резко бьёт по производительности БД.

### OOM Killer — как выбирает жертву

У каждого процесса есть **oom_score** — рейтинг кандидата на убийство.
```bash
cat /proc/PID/oom_score
```
Главный фактор — сколько физической памяти (RSS) реально жрёт процесс. Чем больше — тем выше рейтинг. Логика: убить один процесс с 4 ГБ выгоднее, чем десять по 50 МБ.

Ручная корректировка:
```bash
cat /proc/PID/oom_score_adj    # диапазон -1000..+1000
```
-1000 — процесс неприкасаем (например sshd, чтобы можно было зайти и разобраться при нехватке памяти), +1000 — приоритетная жертва.

Диагностика после инцидента:
```bash
dmesg | grep -i "out of memory"
dmesg | grep -i "killed process"
journalctl -k | grep -i oom
```

## /proc/sys/vm — параметры поведения ядра

```bash
ls /proc/sys/vm
```

- **swappiness** — насколько активно уходить в swap (разобрано выше)
- **dirty_background_ratio** (обычно 10) — при этом % грязных страниц от памяти начинается фоновый сброс на диск, без остановки программ
- **dirty_ratio** (обычно 20) — при этом % ядро принудительно останавливает записывающие процессы, пока не разгребёт грязные страницы — заметно тормозит систему
- **dirty_expire_centisecs** (обычно 3000 = 30 сек) — страница, грязная дольше этого времени, сбрасывается принудительно, даже если объём небольшой
- **overcommit_memory** — 0 (эвристика, разумный дефолт), 1 (разрешать всегда), 2 (строго, никогда не обещать больше реального объёма)
- **min_free_kbytes** — минимальный резерв свободной памяти, который ядро никогда не отдаёт обычным процессам (нужен для собственных критичных операций ядра, чтобы не оказаться в ситуации замкнутого круга при полном исчерпании памяти)

## Три уровня кэша процессора (L1/L2/L3)

Не путать с buff/cache из `free -m` — это два разных механизма:
- **L1/L2/L3** — аппаратный кэш прямо на кристалле процессора, между CPU и ОЗУ
- **buff/cache** — программный кэш файловой системы Linux, живёт в самой оперативке

Зачем нужен кэш процессора — ОЗУ не настолько быстрая, как само ядро CPU, без кэша процессор постоянно бы простаивал в ожидании данных.

Иерархия по скорости и размеру, от быстрого/маленького к медленному/большому:
- **L1** — самый быстрый, самый маленький (32-64 КБ на ядро), разделён на L1i (инструкции) и L1d (данные)
- **L2** — больше (256 КБ - 1 МБ), чуть медленнее, обычно свой у каждого ядра
- **L3** — самый большой (несколько МБ), самый медленный из трёх, обычно общий для всех ядер процессора

```bash
lscpu | grep -i cache
```

Цепочка по скорости: регистры → L1 → L2 → L3 → ОЗУ → диск/swap.

## HugePages и Transparent HugePages (THP)

### Проблема, которую решают

Стандартная страница 4 КБ означает, что для программы с большим объёмом памяти (например 4 ГБ) в таблице страниц нужен больше миллиона записей. Процессору приходится часто транслировать адреса через огромную таблицу — накладные расходы.

### HugePages — решение

Страницы увеличенного размера: **2 МБ** (или 1 ГБ на некоторых системах) вместо 4 КБ. Для тех же 4 ГБ понадобится всего ~2048 записей вместо миллиона.

Нужны программам с очень большими и активно используемыми объёмами памяти — классический пример: базы данных с большой SGA (Oracle).

```bash
grep Huge /proc/meminfo
```
```
HugePages_Total, HugePages_Free, HugePages_Rsvd, HugePages_Surp, Hugepagesize
```

Настройка вручную, через `/etc/sysctl.conf`:
```bash
vm.nr_hugepages=<число>
```
Число страниц = размер нужной памяти / Hugepagesize.

### THP — автоматический аналог

Ядро само, без ручной настройки, пытается объединять маленькие страницы в большие через фоновый процесс `khugepaged`.

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
```
Режимы: `always` (везде автоматически), `madvise` (только там, где приложение явно попросило через `madvise()` с флагом `MADV_HUGEPAGE`), `never` (отключено).

На практике THP иногда вредит производительности — фоновый `khugepaged` сам ест CPU и создаёт непредсказуемые паузы. Для баз данных (как в примере с Oracle) обычно рекомендуют THP отключать и настраивать обычные HugePages вручную и явно.

```bash
echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

## Главные выводы

- Все программы работают только с виртуальной памятью и ничего не знают про физическую
- У каждой программы своя личная таблица, где записано соответствие виртуальных адресов физическим страницам
- Кольца защиты и таблица страниц — два разных, но связанных механизма аппаратной защиты (инструкции vs память)
- Физическая память выделяется не заранее целиком, а по требованию, в момент первого реального обращения
- buff/cache в free и L1/L2/L3 кэш процессора — совершенно разные вещи, не путать
- available в free честнее показывает реальный запас памяти, чем free, потому что учитывает вытесняемый кэш
